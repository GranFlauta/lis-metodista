# Registro de Supuestos de Diseño — Fase 1

| # | Tema | Qué no estaba definido | Qué decidí (la opción más segura/simple) | Impacto si está mal |
|---|---|---|---|---|
| 1 | Búsqueda `q` en `/api/usuarios` | Comportamiento exacto de comodines o longitud mínima de búsqueda. | Se aplica búsqueda parcial insensible a mayúsculas (`ILIKE` / `LOWER(...) LIKE %q%`) sobre `usuario`, `nombres`, `apellido_paterno`, `apellido_materno` y `ci`. Si `q` está vacío o ausente, se omite el filtro. | Mínimo; devuelve los resultados esperados por el operador sin errores. |
| 2 | Validación de `correo` en creación/edición | El estándar exacto de RFC o librería externa para correo electrónico. | Se valida con expresión regular simple `^[^@\s]+@[^@\s]+\.[^@\s]+$` sin dependencias adicionales (§6.3). Si viene vacío o nulo, se guarda como `NULL`. | Nulo; evita registrar correos con formato inválido y no introduce dependencias. |
| 3 | Tratamiento de `CITEXT` en SQLAlchemy | Compatibilidad del tipo nativo `citext` con dialectos genéricos de SQLAlchemy. | Se modela como `String` en los modelos SQLAlchemy y se asegura la normalización a minúsculas (`.strip().lower()`) antes de consultar o guardar en base de datos (§11.3). | Nulo; la columna en BD sigue siendo `citext` y el backend garantiza la coherencia. |
| 4 | Redondeo de `minutos_restantes` en 423 `CUENTA_BLOQUEADA` | Método de redondeo cuando el tiempo de bloqueo restante tiene segundos. | Se redondea hacia arriba (`math.ceil`) a minutos enteros, garantizando un mínimo de 1 minuto mientras `bloqueado_hasta > ahora`. | Muy bajo; el usuario siempre sabe cuántos minutos debe esperar como máximo. |
| 5 | Manejo de excepciones de validación Pydantic | Formato del string `mensaje` cuando fallan múltiples campos a la vez. | Se unen los mensajes de cada campo separados por `; ` indicando la ruta del campo afectado (`loc`) y el detalle del error con código HTTP 400 y `codigo: "VALIDACION"`. | Nulo; cumple la especificación de error clínico único y descriptivo. |
| 6 | Verificación de timing en login de usuario inexistente | Cómo ejecutar el dummy hash sin incurrir en overhead excesivo ni degradación. | Se ejecuta `verify_password` contra un hash `DUMMY_ARGON2_HASH` generado al importar el módulo con `secrets.token_urlsafe(16)` para asegurar que el tiempo de respuesta sea indistinguible del de un usuario existente. | Nulo; neutraliza ataques de enumeración y temporización de usuarios. |
| 7 | Uso de `pwdlib` en lugar de `argon2-cffi` directo | La librería de alto nivel para hashing Argon2id. | Se adoptó `pwdlib` con `Argon2Hasher()`, que utiliza `argon2-cffi` por debajo y genera hashes estándar `$argon2id$v=19$...`. Ambas librerías quedaron fijadas en `requirements.txt`. | Nulo; máxima compatibilidad, estándar criptográfico idéntico. |
| 8 | Podman en Fedora y puertos de red | Entorno de contenedores y puertos de Caddy. | Se utiliza Podman (`podman compose`). El puerto HTTPS es `8443:443` con dominio `lis.local` y certificado interno de Caddy. Se removió el mapeo `8080:80` porque la redirección de Caddy omitía el puerto no estándar. | Mínimo; requiere resolver `lis.local:8443` en peticiones cliente. |
| 9 | Superficie de red de PostgreSQL | Exposición del puerto 5432 de la base de datos. | Se eliminó `ports` de `docker-compose.yml` base para que PostgreSQL no sea accesible fuera de la red interna de compose. Para desarrollo se creó `docker-compose.override.yml` atado a `127.0.0.1:5432:5432`. | Positivo; protege la base de datos clínica de accesos en la red local. |
| 10 | Modelos ORM y esquema de BD | Estilo de mapeo SQLAlchemy y esquema explícito. | Se utilizan modelos con `Column`/`declarative_base` en `app/core/database.py`, `models/user.py` y `models/session.py`. El acceso al esquema `laboratorio` se resuelve vía `connect_args={"options": "-csearch_path=laboratorio,public"}`. | Nulo; la Fase 2 mantiene estas convenciones ya establecidas. |
| 11 | Versión de Python del entorno | Discordancia entre host (Python 3.14) y contenedor. | Se alineó `backend/Dockerfile` a `python:3.14-slim`, coincidiendo con `Python 3.14.8` del entorno local. | Positivo; elimina discrepancias de runtime entre desarrollo y contenedor. |
| 12 | Extensiones a la política de claves | Detección de partes del usuario y CI en la clave. | Se segmentan usuarios con puntos/guiones y se prohíben fragmentos de longitud ≥ 3, y secuencias de dígitos del CI de longitud ≥ 4. | Positivo; previene contraseñas triviales basadas en datos del operador. |
| 13 | Recreación de BD de pruebas | Arnés de pruebas con PostgreSQL real y catálogo. | Se creó `scripts/crear_bd_test.sh` (compatible con Docker y Podman) que recrea `lis_test` y aplica `001_schema.sql` y `002_seed_catalogo.sql`. Los tests de integración fallan explícitamente si las tablas o el trigger `trg_proteger_informe` no existen. | Positivo; asegura reproducibilidad estricta sin `create_all` ni `SkipTest`. |
